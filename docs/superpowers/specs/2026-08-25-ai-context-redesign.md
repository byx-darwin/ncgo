# AI Context File Redesign — CLAUDE.md / AGENTS.md / project-context.md

> Design for restructuring ncgo's generated AI context files from
> "template maintainer documentation" to "agent task execution manuals".

Date: 2026-08-25
Status: Draft
Author: gf-workflow / wf-2026-08-25-002

## 1. Problem Statement

The current `ncgo ai sync` renders CLAUDE.md by embedding the **full**
embedded design doc (641 lines Hertz / 692 lines Kitex) under an
"Architecture & Built-in Features" heading. The resulting file is 700+
lines long and organized for ncgo template maintainers, not for AI agents
working in the generated project.

Concrete problems observed:

1. **Information overload** — 700+ lines consumes 15-20% of an 8K context
   window, starving the agent of room for actual problem-solving.
2. **Wrong audience** — the embedded design doc says "Audience: ncgo
   maintainers" and references template-internal paths like
   `internal/assets/_data/hertz/`.
3. **Missing method-level context** — CLAUDE.md lists domains but not what
   methods each domain already has. Agents cannot tell whether a method
   already exists.
4. **No edit boundaries** — agents have no concise reference for which files
   are safe to edit vs which are generated/off-limits.
5. **Error codes buried** — an agent writing error handling must scan
   hundreds of lines to find the right code.
6. **No verification checklist** — the workflow mentions verification but
   there is no concise "run these commands to confirm" section.
7. **Staleness invisible** — the generated-at marker is not at the top, so
   an agent cannot quickly assess freshness.

## 2. Goals

- Reduce CLAUDE.md to ~150 lines while preserving all information an
  agent actually needs day-to-day.
- Add method-level context from `scan.Scan()`.
- Add explicit edit boundaries.
- Add error-code quick reference.
- Add verification checklist.
- Keep the full design doc available as a separate standalone file
  (`docs/ncgo/`) for deep-reference use cases.
- Apply the same restructuring to AGENTS.md and project-context.md.

## 3. Non-Goals

- This design does **not** add new CLI commands (`ai context`, `ai status`)
  — those are separate improvements (see audit items #1, #3).
- This design does not change the managed-marker / Force / DryRun
  overwrite contract.
- This design does not change the template handoff ordering (`make sqlc`
  before `go mod tidy`).
- This design does not implement the deferred `architecture.md` (PRD §6
  row 4, which requires go/parser domain-port scanning).

## 4. Target Structure

### 4.1 CLAUDE.md (~150 lines)

```markdown
<!-- ncgo:managed -->
<!-- ncgo:generated-at: 2026-08-25T00:00:00Z -->

# Project Context for Claude Code

> Auto-generated by `ncgo ai sync` from `.ncgo/manifest.yaml`.
> This file is a task-oriented summary; the full design reference lives
> at `docs/ncgo/<profile>/design-doc.en.md`.

## Quick Facts

- module: `github.com/acme/user-api`
- service.name: `user-api`
- service.kind: `hertz`
- service.with_database: `true`
- domains: `[device, user]`
- infra: `[redis]`
- ncgo: `0.1.0` (assets `test`)

### Methods

- **device**: `Create`, `Get`, `List`, `Update`
- **user**: `Create`, `Get`, `Delete`

## Boundaries

### You may edit

| Path | Purpose |
|------|---------|
| `internal/usecase/<domain>/` | Business logic |
| `internal/handler/<service>/` | HTTP handlers |
| `internal/adapter/` | Outbound RPC clients |
| `internal/repository/<domain>/` | Data access implementations |
| `internal/pkg/middleware/` | Custom middleware |
| `internal/base/server/server.go` | DI wiring |

### Do not edit

| Path | Why |
|------|-----|
| `internal/usecase/<domain>/<domain>.go` between anchors | Generated method stubs |
| `internal/base/data/` | Generated data layer |
| `internal/db/gen/` | sqlc-generated code |
| `internal/router/register.go` | hz-generated routes |
| `internal/pb/` | Protobuf generated types |
| `CLAUDE.md`, `AGENTS.md` | Managed by `ncgo ai sync` |

## Layer Rules

```
main → base/server → router, handler/*, middleware
handler/* → usecase/*, pkg/response, pb        (no repo / data import)
usecase/* → adapter, repository (ports), pb    (no hertz import)
repository/* → base/data, db/gen               (no usecase import)
```

- All errors are `goerror` chains carrying a numeric `Code` + `Public` msg.
- Handlers use `response.OK(c, resp)` / `response.Err(c, err)`.
- Do not store `*app.RequestContext` in struct state.

## Error Codes

| Code | Name | HTTP | Meaning |
|------|------|------|---------|
| 10000 | CodeSystem | 500 | System error |
| 10001 | CodeParamInvalid | 400 | Bad request |
| 10002 | CodeAuthFailed | 401 | Auth failure |
| 10004 | CodeConfigInvalid | 500 | Config error |
| 10200 | CodeRateLimited | 429 | Rate limited |
| 10203 | CodeIdempotencyKeyMissing | 400 | Missing idempotency key |
| 10204 | CodeIdempotencyConflict | 409 | Idempotency conflict |
| 40100+ | Business codes | 200 | Application-defined |

Business codes (`>= 40100`) fallback to HTTP 200. Register fine-grained
statuses with `goerror.RegisterHTTPStatuses` when non-200 is required.

## Workflow

1. **Add domain** — `ncgo add domain <name> --root .`
2. **Add method** — `ncgo add method <domain>.<Method> --root .`
3. **Regenerate DB** — `make sqlc` (Kitex always; Hertz only with DB)
4. **Refresh context** — `ncgo ai sync --root .`

Full reference: `docs/ncgo/hertz/design-doc.en.md`

## Verify

```bash
go build ./...            # compiles
go vet ./...              # static analysis
ncgo check --root .       # ncgo consistency (anchors, manifest, context)
ncgo ai sync --root .     # re-render after changes
ncgo check --root .       # confirm stale-context check passes
```

## 5. Implementation Plan

### 5.1 Changes to `internal/ai/render.go`

| Function | Change |
|----------|--------|
| `renderClaude()` | Replace full design-doc embedding with the new structure |
| `renderAgents()` | Same restructuring |
| `renderProjectContext()` | Same restructuring |
| `buildInputs()` | Add `MethodsByDomain` and `ErrorCodes` to `renderInputs` |
| `writeProjectFacts()` | Add methods listing after facts |
| `writeArchitectureSummary()` | Add a `summaryOnly bool` param for project-context.md |

### 5.2 Changes to `internal/ai/sync.go`

| Function | Change |
|----------|--------|
| `Sync()` | Call `scan.Scan()` to populate method context (only when usecase dir exists) |
| `renderInputs` struct | Add `MethodsByDomain map[string][]string` and `ErrorCodes string` fields |
| `buildInputs()` | Populate new fields from scan result |

### 5.3 New internal helper

Add `internal/ai/boundaries.go`:

```go
// editBoundaries returns the may-edit / do-not-edit file tables.
func editBoundaries(source syncSource) (mayEdit, doNotEdit []boundaryEntry)
```

Add `internal/ai/errorcodes.go`:

```go
// errorCodesSummary returns the condensed error-code table for a profile.
func errorCodesSummary(profile string) string
```

### 5.4 Changes to `internal/ai/generated_at.go`

Move the generated-at marker to **immediately after** the managed marker
line (line 2) so agents can assess freshness without scrolling.

### 5.5 Error code data source

Error codes are currently scattered across the embedded design doc.
Extract them into a structured asset:

```
internal/assets/_data/docs/<profile>/error-codes.en.md
```

Or define them as a Go constant map in `internal/ai/errorcodes.go`.
The latter is preferred — it keeps the source of truth in code and
avoids a new asset file.

### 5.6 Boundary rules data source

Boundary rules are partly static (always-generated files like
`internal/db/gen/`) and partly manifest-derived (usecase paths from
`m.Domains`). The static portion lives in `internal/ai/boundaries.go`;
the dynamic portion is computed from the manifest in `renderClaude()`.

## 6. Migration & Compatibility

| Concern | Handling |
|---------|----------|
| Existing managed files | Re-rendered on next `ai sync`; new structure applies |
| Non-managed files | Still skipped unless `--force` |
| `ncgo check` stale detection | Still works — it parses the `- domains:` fact line, which is preserved |
| `ncgo check` context file list | `contextFileTargets()` unchanged |
| MCP `ai sync` tool | Same `ResultFields`, same `Result` struct — output shape unchanged |
| Golden tests | Must be regenerated with `-update-golden` |
| Standalone docs (`docs/ncgo/`) | Still written with full design doc for deep reference |

## 7. Testing Strategy

| Level | What |
|-------|------|
| Unit | `errorCodesSummary()` returns expected codes per profile |
| Unit | `editBoundaries()` returns correct tables for mono vs workspace |
| Unit | `renderClaude()` output contains all required sections |
| Integration | `Sync()` with a real manifest produces the new structure |
| Golden | Regenerate `internal/scaffold/mono/testdata/` golden files |
| Smoke | `ncgo ai sync --root . --target all` in a generated project |

## 8. Open Questions

1. **Methods from scan vs from manifest** — should we show methods from
   `scan.Scan()` (real code) or from manifest? Recommendation: scan, since
   it reflects reality. Fall back to manifest if scan fails.

2. **Error code coverage** — should we show all codes or just the common
   ones? Recommendation: common ones (~10 codes) in CLAUDE.md; full table
   in the standalone `docs/ncgo/` design doc.

3. **project-context.md scope** — should it also get methods + boundaries,
   or stay minimal? Recommendation: add methods (facts-only), skip
   boundaries (those live in CLAUDE.md/AGENTS.md).

4. **Should the full design doc still be embedded as a collapsible
   section?** Recommendation: no — it bloats the file. The standalone
   `docs/ncgo/` copy serves deep-reference needs.
