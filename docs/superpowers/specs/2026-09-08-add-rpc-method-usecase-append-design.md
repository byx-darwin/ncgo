# Design: `ncgo add rpc-method` — append IDL-derived RPC stubs to existing top-level usecase.go

## Context

User report: after adding an RPC to an existing kitex service's proto and
running `make update`, they had to hand-edit `handler.go` ("merge generated
interface") and add 6 placeholder not-implemented methods to a project-owned
`composite.go` just to get `go build` passing. They initially attributed this
to `ncgo add method` generating a stub with a fixed, argument-less signature
(`func (u *UseCase) Method() error`).

## Investigation

- `ncgo add method` (`internal/scaffold/method/method.go`) only ever targets
  the **domain-layer** usecase file
  (`internal/usecase/<domain>/<domain>.go`, created by `ncgo add domain`).
  It has no knowledge of IDL and is unrelated to kitex/hz code generation.
  This command's behavior is unchanged by this design and is intentionally
  documented (`ncgo-dev-workflow.*.md` step 5) as requiring manual handler
  wiring — that part is by design, not a defect.
- The kitex custom templates
  (`internal/assets/_data/kitex/kitex-template/`) drive the **top-level RPC**
  layer:
  - `handler.yaml` has `update_behavior: cover` — `make update` always
    rewrites `handler.go` in full, driven by `.ServiceInfo.Methods`. A newly
    added RPC in the proto **automatically appears** in `handler.go`.
  - `usecase.yaml` has `update_behavior: skip` — once `usecase.go` exists,
    kitex's own generator never touches it again. A newly added RPC's method
    is **not** appended automatically; the user must hand-write it to satisfy
    the interface the freshly-`cover`-regenerated `handler.go` expects.
- Confirmed with the user: the method they hand-added lives in this
  **top-level RPC usecase.go**, not the domain-layer file `ncgo add method`
  manages. `composite.go` is a project-owned aggregation/decorator file not
  generated or tracked by ncgo anywhere in the repo — out of scope here.

### Mechanism (revised after prototyping — see below)

Two mechanisms were considered and rejected before landing on the final one:

1. **Parse the proto directly and map message names to Go types.** Rejected:
   the "message name → generated Go type name + import path (with kitex's
   `PkgRefName`/`ImportPath` aliasing rules)" mapping is computed internally
   by the kitex CLI's own template data (`.ServiceInfo`) and has no
   equivalent anywhere in this repo. Reimplementing it would duplicate kitex
   internals and risk drifting from what kitex itself actually generates.
2. **Re-invoke kitex/hz generators into a scratch copy to regenerate
   `usecase.go` fresh, then diff out the new method.** Rejected: requires
   shelling out to the real generator (plus, for kitex, a working
   `protoc`/`protoc-gen-go` toolchain) a second time, and depends on being
   able to reconstruct an equivalent scratch project layout. Higher
   operational risk for no benefit over option 3.
3. **Parse the already-generated handler file with `go/ast` and copy its
   type-correct signature.** By the time a user runs this command, they have
   already run `make update` (kitex) or `hz update` (hz) per the documented
   workflow, so a handler file with the new method's *real, compiler-correct*
   Go signature already exists on disk. Prototyped both cases directly:

   - **kitex**: `internal/handler/<service>/handler.go` (`update_behavior:
     cover`, generated by
     `internal/assets/_data/kitex/kitex-template/handler.yaml`) contains
     `func (s *<Service>Impl) <RPC>(ctx context.Context, <args>) (resp
     <Type>, err error)` per method — a plain function declaration with a
     fully resolved signature and matching import block.
   - **hz**: verified by scaffolding a real `ncgo new --kind hertz` project
     and inspecting the generated
     `internal/handler/<pkg>/<service>.go`. ncgo's own `customize_layout`
     (`template/layout.yaml` + `template/package.yaml`) generates a genuinely
     typed Go interface, not just an HTTP-context function:
     ```go
     type useCase interface {
         Ping(ctx context.Context, req *pb.PingReq) (*pb.PingResp, error)
     }
     ```
     This is exactly as reliable as kitex's function declaration — no need to
     parse `c.BindAndValidate(...)` call sites inside a handler body, which
     was an earlier, rejected, more fragile idea.

   Option 3 needs **no IDL parsing at all** (proto or thrift) — it reads
   already-compiled-against, already-correct Go source. This also removes
   the "thrift not supported" restriction from earlier design iterations:
   thrift-derived projects still produce a real Go handler signature the
   same way proto-derived ones do.

## Decision

Add a new, independent CLI command `ncgo add rpc-method` (not a flag on
`add method`, to keep domain-layer and top-level-RPC semantics from
blurring) that appends a single method stub to an existing top-level
`usecase.go`, with its signature copied from the already-generated handler
file.

### Scope

- **kitex and hz, proto or thrift** — no IDL parsing is involved, so IDL
  format is not a constraint. The command depends on the **handler file
  already existing with the target method** (i.e. the user has already run
  `make update` / `hz update` after editing the IDL). If it doesn't, the
  command errors telling the user to run that first.
- **`composite.go`-style downstream aggregation files remain explicitly out
  of scope** — they are not ncgo-owned artifacts anywhere in the codebase.
- `ncgo add method` (domain layer) is unchanged.

### CLI / orchestrator surface

- `internal/cli/add.go`: new `newAddRPCMethodCmd`, flags `--service <name>
  --rpc <MethodName>` (plus existing `--root`/`--output` conventions).
- `internal/orchestrator/add.go`: new `RunAddRPCMethod`, thin wrapper
  matching `RunAddMethod`'s pattern, reused by CLI and a new MCP tool
  `ncgo_add_rpc_method`.
- Implementation lives in `internal/scaffold/method` (new file, e.g.
  `rpc.go`) — reuses existing manifest-reading and file-writing helpers
  rather than introducing a new package.

### Flow

1. Read `.ncgo/manifest.yaml` to resolve the service kind (`hertz` |
   `kitex`) and confirm `--service` matches `manifest.Service.Name` (mono
   only has one service; this also future-proofs a later micro-workspace
   extension without a breaking flag change).
2. Locate the candidate handler file(s):
   - kitex: `internal/handler/<service>/handler.go` (deterministic single
     path, from `manifest.Service.Name`).
   - hz: walk `internal/handler/**/*.go` looking for a
     `type useCase interface { ... }` declaration containing a method named
     `--rpc`. (Deterministic single path isn't available for hz because the
     handler package directory name is derived from the IDL's `go_package`,
     not the service name.)
3. Parse the matching file with `go/parser`; extract, for the method named
   `--rpc`:
   - kitex: the `*ast.FuncDecl` whose `Name.Name == rpc` and whose receiver
     type ends in `Impl` — its `Type.Params` (excluding the first `ctx`
     param, which is re-added explicitly) and `Type.Results`.
   - hz: the `*ast.InterfaceType` method matching `rpc` inside the `useCase`
     interface — its `Params`/`Results` the same way.
   - Not found → error: "run `make update`/`hz update` first — RPC method
     %q not found in generated handler %q".
4. Resolve the import paths needed by the extracted param/result type
   expressions by cross-referencing the source file's own `*ast.File.Imports`
   (matching package selector identifiers, e.g. `pb.PingReq` → the import
   whose local name is `pb`).
5. Render `func (u *UseCase) <RPC>(ctx context.Context, <args>) (<results>) {
   ... }` into `usecase.go`, matching the "not implemented" body idiom
   already used by the kitex `usecase.yaml` template
   (`goerror.In(...).Code(10010).Public("not_implemented").Errorf(...)`) so
   the appended stub looks identical to what the generator would have
   produced had `usecase.go` not existed yet. Append as a new top-level
   function at the end of the file (no anchor needed), merge in any missing
   imports, then `gofmt`.
6. If a method with that name already exists in `usecase.go`, refuse with a
   clear error instead of producing a duplicate/duplicate-import build
   failure.

### Error handling

- `--service` doesn't match the manifest's service name → explicit error.
- Handler file / matching method not found → explicit error instructing the
  user to run `make update` / `hz update` first.
- Method already present in `usecase.go` → explicit refusal, no partial
  write.
- Extracted type expression references an identifier whose import cannot be
  resolved from the handler file's own import block → explicit error naming
  the type and the handler file (should not happen in practice since the
  handler file itself compiles, but guarded rather than silently emitting
  broken code).

## Scope boundaries

- No changes to `ncgo add method`, `add domain`, or any golden-tested mono
  scaffold output.
- No IDL (proto/thrift) parsing anywhere in this feature.
- No automated handling of downstream, non-ncgo-owned files
  (`composite.go` or equivalent).
- No change to `update_behavior` semantics of existing kitex/hz templates.
- Requires the handler file to already reflect the target method (i.e. the
  generator step has already run); this command does not itself invoke
  `hz`/`kitex`.

## Testing

- New unit tests in `internal/scaffold/method` (sibling to
  `method_test.go`), using minimal fixture handler files written directly as
  Go source (mirroring the real generated shape captured above — a small
  `internal/handler/<service>/handler.go` for the kitex case, a small
  `internal/handler/<pkg>/<file>.go` with a `useCase` interface for the hz
  case), covering: successful append (signature + import correctness) for
  both kitex and hz, method not found in handler, duplicate method in
  usecase.go, `--service` mismatch.
- No new mono-level golden test required — this is a single-file append,
  consistent with `method_test.go`'s existing (non-golden) style.
- Full validation: `go build ./... && go vet ./... && go test ./... -count=1`.

## Documentation

- README.md / docs/examples.md (English + Chinese) gain a section on
  `ncgo add rpc-method`, explicitly stating it must run *after*
  `make update`/`hz update`, and the existing workflow docs
  (`ncgo-dev-workflow.*.md`) get a step referencing it for the usecase.go
  gap, with an explicit note that `composite.go`-style downstream files
  remain manual.
