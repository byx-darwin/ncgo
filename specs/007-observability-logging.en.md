# ncgo Observability & Logging System Design

- Status: v1
- Scope: Hertz and Kitex services generated by ncgo
- Full design (ZH): [007-observability-logging.zh-CN.md](./007-observability-logging.zh-CN.md)

## 1. Overview

A unified logging layer for ncgo-generated services. Business code uses `github.com/samber/oops` to express error semantics; the logging layer parses oops errors into structured fields, routes them by category, and outputs to console, files (with rotation and compression), or both. LoongSuite Go Agent handles trace/metrics auto-instrumentation; the logging layer reads trace context but does not initialize the OTel SDK.

## 2. Architecture

```
Business code (oops errors)
    |
    v
Unified logging helper
    |-- console writer
    |-- typed file writers (per category)
    |-- rotated + gzipped files
    |-- trace/request/release/canary context enrichment
    v
Log collection system / local files / console
```

## 3. Key Design Decisions

### Output Modes

| Mode   | Use Case                          |
|--------|-----------------------------------|
| console | Containers / Kubernetes (stdout) |
| file    | VM / bare metal                   |
| both    | VM with local retention           |
| none    | Disabled                          |

### Log Categories

Eight built-in categories, each routed to its own file: `access`, `error`, `biz`, `rpc`, `db`, `panic`, `audit`, `security`.

### oops Structured Parsing

The logging layer extracts structured fields from oops-wrapped errors:
`error.code`, `error.public`, `error.tags`, `error.scope`, `error.attrs.<key>`, `error.cause`, `error.message`.

Automatic category routing is planned based on oops tags (e.g., `database` tag maps to `db` category) and code ranges.

### Standard Fields

Every log entry includes: `ts`, `level`, `category`, `msg`, `service.name`, `service.kind`, `service.version`, `release.track`, `release.git_sha`, `request_id`, `request_id_source`, `trace_id`, `span_id`, `traffic.lane`.

### Separation of request_id and trace_id

- `trace_id` -- distributed tracing ID from LoongSuite/OTel/upstream.
- `request_id` -- business correlation ID for log search and cross-system troubleshooting.
- Fallback chain: incoming header > trace_id > generated ID.

## 4. Configuration Model

```yaml
logging:
  enabled: true
  mode: both          # console | file | both | none
  format: json        # json | text
  level: info
  add_source: true
  console:
    enabled: true
    color: false
  file:
    enabled: true
    dir: logs
    filename: app.log
    max_size_mb: 100
    max_backups: 10
    max_age_days: 30
    compress: true
  categories:
    access:  { enabled: true, file: access.log,  level: info }
    error:   { enabled: true, file: error.log,   level: error }
    biz:     { enabled: true, file: biz.log,     level: warn }
    # ...
  context:
    request_id: true
    trace_id: true
    span_id: true
    release: true
    canary: true
```

## 5. CLI / MCP Interface

```bash
# Add logging optional to an existing project
ncgo add infra observability_logging --root .
ncgo add infra logging --root .          # alias

# Wire into server/client code automatically
ncgo add infra logging --root . --wire

# Preview changes (no files modified)
ncgo add infra logging --root . --wire --dry-run

# Machine-readable plan
ncgo add infra logging --root . --wire --plan
```

JSON plan entries: `file/create`, `wire/update`, `manifest/add`, `wire/add_import`, `wire/insert_logging_init`, `wire/replace_middleware`, `wire/insert_client_middleware`, `next_step/run`.

## 6. Generated Files

```
internal/base/logging/logging.go   # Core: config, logger, context, category, file, oops
internal/base/logging/hertz.go     # Hertz middleware (recovery, request_id, access_log)
internal/base/logging/kitex.go     # Kitex interceptors (request_id, access_log, recovery)
```

## 8. Recommended Strategy

| Environment      | Mode    | Format |
|------------------|---------|--------|
| Local dev        | console | text   |
| Container prod   | console | json   |
| VM prod          | both    | json + compressed files |

## 9. Integration with Canary Release

Log entries automatically include `release.track`, `service.version`, and `traffic.lane`, enabling canary-vs-stable error comparison queries.
