# ncgo Canary Release System Design

- Status: v1
- Scope: Hertz and Kitex services generated by ncgo
- Full design (ZH): [006-canary-release.zh-CN.md](./006-canary-release.zh-CN.md)

## 1. Overview

Canary release capability for ncgo-generated Hertz (HTTP) and Kitex (RPC) services. The system uses Nacos or Polaris as the registry, service discovery, and config center, with a unified canary rule engine running locally in each service.

## 2. Architecture Philosophy

Canary logic should not live in business handlers or usecase code. Instead, ncgo promotes a four-layer split:

1. **Release layer** -- CI/CD, Kubernetes, Argo Rollouts, manual/auto rollback.
2. **Traffic layer** -- Ingress/Gateway/Service Mesh, Kitex client selector.
3. **Registry/Discovery/Config layer** -- Nacos or Polaris for registration, discovery, instance metadata, and dynamic canary rules.
4. **Observability layer** -- Logs, metrics, and traces aggregated by version and traffic lane.

## 3. Key Design Decisions

### Unified Canary Rule Model

A provider-neutral YAML schema that maps to both Nacos and Polaris:

```yaml
version: 1
enabled: true
service: user-rpc
default_track: stable
fallback: stable
rules:
  - name: header
    priority: 100
    match:
      headers:
        X-Traffic-Lane: canary
    route:
      track: canary
  - name: percentage
    priority: 10
    match: {}
    route:
      weighted:
        stable: 95
        canary: 5
```

### Release Tracks

| Track   | Meaning                              |
|---------|--------------------------------------|
| stable  | Current stable version, carries most traffic |
| canary  | New version, small percentage of traffic      |

### Instance Metadata

Every instance registers with metadata keys: `service.name`, `service.kind`, `service.version`, `release.track`, `release.git_sha`, `release.build_time`, `release.env`. These flow into registration metadata, logs, traces, metrics, and `/version` endpoints.

### SDK-Neutral Seams

The code generation is SDK-neutral. It provides `Discoverer`, `RuleProvider`, and `Selector` abstractions. Real Nacos or Polaris SDK adapters can be plugged in later without changing the business contract.

## 4. Hertz Strategy

- Heavy traffic splitting at the Gateway/Ingress/Mesh layer (weight-based or header/cookie/user/tenant).
- Hertz services keep it light: expose `/version`, enrich logs/traces with `release.track`, read `X-Traffic-Lane` into context, propagate lane to downstream Kitex calls.
- Do NOT hardcode canary business branches in handlers.

## 5. Kitex Strategy

- Use registry metadata + client-side selector.
- Stable and canary instances share the same Kitex service name, differ only by `release.track` metadata.
- Selector picks instances by: explicit lane header > tenant/user match > percentage > default stable > fallback.
- Propagate `traffic.lane`, `traffic.user_id`, `traffic.tenant_id` via Kitex metadata.

## 6. CLI / MCP Interface

```bash
# Add canary optional to an existing project
ncgo add infra release_canary --root .
ncgo add infra canary --root .          # alias

# Wire into server/client code automatically
ncgo add infra canary --root . --wire

# Preview changes (no files modified)
ncgo add infra canary --root . --wire --dry-run

# Machine-readable plan
ncgo add infra canary --root . --wire --plan
```

JSON plan entries: `file/create`, `wire/update`, `manifest/add`, `wire/insert_traffic_middleware`, `wire/insert_client_middleware`, `next_step/run`, and more.
